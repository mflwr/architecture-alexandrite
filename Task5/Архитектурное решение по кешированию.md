# Архитектурное решение: Внедрение кеширования в MES

## Мотивация

### Проблемы
1. **Низкая производительность дашборда MES**
    - Операторы жалуются на долгую загрузку страницы с заказами.
    - Фильтрация и пагинация не решили проблему полностью.
2. **Рост нагрузки после открытия API**
    - Увеличилось количество жалоб на задержки как от B2C-клиентов, так и API-партнеров.
3. **Длительный расчет стоимости**
    - Процесс занимает до 30 минут для сложных моделей, блокируя другие операции.

### Цели кеширования
- Ускорить доступ к часто запрашиваемым данным:
    - Список новых заказов (статусы `MANUFACTURING_STARTED`, `MANUFACTURING_APPROVED`)
    - Результаты расчетов стоимости
- Снизить нагрузку на PostgreSQL (MES DB)
- Улучшить отзывчивость UI для операторов

## Предлагаемое решение

### Выбор типа кеширования
**Серверное кеширование** (Redis/Memcached) | **Паттерн: Cache-Aside**

| Клиентское                                            | Серверное                                                         |
|-------------------------------------------------------|-------------------------------------------------------------------|
| Не подходит: динамические данные требуют актуальности | Оптимально: централизованное управление, контроль согласованности |

**Обоснование паттерна**
- **Cache-Aside**
    - Чтение: кеш → БД (с последующим обновлением кеша)
    - Запись: БД → инвалидация кеша
- **Почему не другие**
    - Write-Through: увеличивает latency записи (критично для статусов)
    - Refresh-Ahead: избыточная сложность для текущего сценария

## Стратегия инвалидации
**Гибридная (TTL + Программная)**

**По событию изменения**
- Инвалидация кеша при изменении статуса заказа
- Пример: удаление ключей orders:* при переходе в MANUFACTURING_STARTED

**TTL (60 сек)**

- Для защиты от "залипания" устаревших данных
- Оптимально для данных, где задержка в 1 мин допустима

**Сравнение стратегий**


| Стратегия       | 	Преимущества                     | 	Недостатки                          |
-----------------|-----------------------------------|--------------------------------------
| Временная (TTL) | 	Простая реализация               | 	Риск устаревания данных             |
| По ключу	       | Точечная инвалидация              | 	Сложность отслеживания ключей       |
| Программная     | 	Максимальная актуальность данных | 	Требует интеграции с бизнес-логикой |


### Дополнительные рекомендации

**Кеширование расчетов стоимости**

- Ключ хэш 3D-модели
- TTL 24 часа (баланс между актуальностью и производительностью)

**Мониторинг**

- Hit/Miss Ratio для кеша
- Среднее время ответа MES_API

**Оптимизация запросов**

- Добавить индексы по полю status в MES_DB
- Вынести подсчет заказов по статусам в отдельную материализованную view
